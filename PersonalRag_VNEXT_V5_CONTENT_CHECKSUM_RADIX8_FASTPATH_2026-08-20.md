# PersonalRag vNext v5 Content Checksum / Adaptive Radix8 FastPath

**Date:** 2026-08-20  
**Baseline:** `PersonalRag_GUI_PortableCore_VNextPeriodicQ3ReuseFastPath_2026-08-20.zip`  
**Baseline SHA-256:** `d79fc30a7d3c493963ef3250427e4c3a0599f41d6ea059a4cb7cd9598e0a7ecd`

## Summary

This wave removes a redundant full-content FNV-1a pass from vNext segment construction and reduces q3 radix fixed overhead for the small post-dedup shards that dominate the measured workload.

Accepted changes:

1. **PRSEG2A5 / format v5**
   - New writers emit `PRSEG2A5`, version 5, footer `PR2FTR05`.
   - The content section's standalone checksum field is zero in v5.
   - The existing 64-bit whole-file FNV-1a remains mandatory and covers the header, section descriptors, all section bytes, alignment padding, and therefore the complete content blob.
   - The other 13 section-level checksums remain unchanged.
   - Strict/open and published-fast paths verify the whole-file checksum before trusting sections.
   - The reader continues to accept legacy `PRSEG2A4` / version 4 segments and verifies their legacy content section checksum.

2. **Adaptive q3 radix8 fast path**
   - For q3 shards with at most 32,768 `(suffix, owner)` packed values, sorting uses stable two-pass 8-bit LSD radix with 256 counters.
   - Large shards retain the existing 65,536-counter upper-16 radix path.
   - The large 65,536-counter scratch vector is allocated lazily only when the fallback is actually needed.
   - Stable ordering and serialized q3 bytes are preserved.

## Why v5 is safe

v4 performed two FNV-1a passes over the same large content bytes during a build:

- one standalone content-section checksum;
- one whole-file checksum while the segment is streamed to disk.

These are not independent integrity mechanisms: both use the same FNV-1a algorithm, while the whole-file checksum already covers the exact content bytes and their descriptor. v5 removes only the redundant standalone content-section pass; it does **not** remove whole-file corruption detection.

A dedicated corruption test flips a byte inside v5 content without repairing the footer and confirms strict open fails with `file checksum mismatch`.

## Actual v4 compatibility oracle

A real v4 segment was generated by the previous canonical writer using 5,000 documents × 4,096-byte payload. A v5 segment was generated from the identical deterministic input.

Both segment files are exactly 21,869,176 bytes.

The v5 file was transformed to v4 **only** by:

- changing A5 magic/version/footer metadata to A4/version 4;
- calculating the legacy standalone content FNV field;
- recalculating the existing whole-file FNV footer.

After that transformation, it was byte-for-byte identical to the actual v4 writer output:

```text
actual v4 SHA-256:
0917d6164be3a3da8c2a26cfc372e68faa8d29035e89c79374ca189d3e2e6326

v5 transformed to v4 SHA-256:
0917d6164be3a3da8c2a26cfc372e68faa8d29035e89c79374ca189d3e2e6326

BYTE_IDENTICAL_TO_ACTUAL_V4 = true
```

The new reader was also directly tested against the actual previous-writer v4 segment and opened all 5,000 documents successfully.

`CURRENT` and the generation manifest produced by the old and new builders were also byte-identical for this single-segment oracle store.

## Rejected experiments in this wave

The following experiments were measured and removed:

- q3 traversal + content checksum fusion: approximately 5.7% end-to-end regression; FNV scalar work destroyed the benefit of the optimized suffix comparison.
- manual 8-byte FNV loop unroll: no reliable improvement; FNV dependency chain remained dominant.
- content `write_vectored`: `write_stream` improved about 13%, but end-to-end did not win reliably and the Linux-oriented result was not sufficient to justify risk to Windows production behavior.
- q3 encode aggressive reserve/rank variant: no reliable end-to-end win and was not retained.

## Remaining bottleneck

After this wave, CPU-side content checksum work is no longer dominant. The profile now makes these relatively more important:

- q3 emit / scatter / encode;
- path-index construction for smaller content workloads;
- durable `write_stream` and especially real-storage `sync_all()` latency.

Any future on-disk format work must retain v4/v5 read compatibility unless an explicit migration plan supersedes it.
